## Blocking and major findings

### P0 — No clean end-to-end installed-app proof

The app has working subsystems and manually repaired real projects, but it has not completed the mixed-device, partial-ingest, later-source, intelligence, Resolve-update, relaunch, and cleanup-choice workflow without Codex or CLI assistance.

Impact: the product cannot yet be trusted to replace the manual workflow it promised to remove.

Action: execute `EXECUTION_PLAN.md` through Gate 7 and keep status `in progress`.

### Resolved during this audit — Import plan had no undo/redo

Move, split, and merge previously mutated the in-memory proposed grouping immediately. The user had already accidentally pressed `Split into New Shoot` and had no obvious recovery.

Implemented in this pass: reversible plan snapshots, Undo, Redo, Reset Groups, Command-Z/Shift-Command-Z, selection reconciliation, and a sidecar-preservation regression test.

Installed evidence: on the real scanned card, Split changed 7 proposed shoots to 8, Undo restored 7, all 201 videos remained assigned exactly once, and a final read-only rescan cleared temporary history. No shoot was selected or copied. Full multi-action/window-size verification remains in Gate 1.

### P0 — Automatic intelligence remains incomplete as a general system

Andaan was manually brought to a stronger package, but fixed profile recipes and one-project repair do not prove evidence-adaptive categories, interview/take separation, later-source invalidation, or automatic package generation across project types.

Impact: the app can say a project is ready while omitting the exact visual/narrative organization the user expected.

Action: implement Gate 4 and benchmark multiple real project types.

### P0 — Later-source Resolve updates are not proven idempotent

The app can create packages and list/reopen timelines, but later camera/recorder arrival has not been shown to update the same intended project/package exactly once.

Impact: duplicate timelines, stale SELECTS, or second projects can appear during ordinary ongoing work.

Action: stable Resolve object identities, reconciliation, and repeat/live update tests.

### P1 — Critical import decisions are vertically remote

At 1228×768, the first shoot card begins at the bottom of the viewport after source/status explanation. Per-shoot destination and take review require substantial scrolling.

Impact: the user cannot see the source, selection total, destination, and confirmation context together; errors become likely.

Action: compress source chrome, use a two-pane or sticky-plan layout, and keep per-shoot include/destination in the collapsed row.

### P1 — Text and controls remain too small

Navigation, source paths, metrics, badges, chat text, Activity metadata, and several 12–13.5 point fixed-size labels are visibly small at the actual window.

Impact: sustained use is tiring and essential distinctions are missed.

Action: adopt a macOS type/spacing floor, test system text scaling, and stop using compact metadata as the default body language.

### P1 — Chat demonstrated stale operational facts

Project Chat stated 41 clips/540 samples before later correcting to 31/403.

Impact: the user cannot trust chat to explain the current project, and may trigger the wrong action.

Action: generate operational facts exclusively from current deterministic state at response time; add stale-state regression tests.

### P1 — Search result action association is unproven

The user performed two searches and could not tell which search the timeline button would materialize.

Impact: a correct backend action can still create the wrong editorial artifact from the user's perspective.

Action: bind result set, selection, query, proposed name, preview, and confirmation into one stable search-session object.

### P1 — Search identity and score explanation remain weak

Source paths and labels exist in models, but duplicate-filename visual proof is absent. Previous result rows exposed unexplained decimal scores.

Impact: users cannot distinguish identical filenames across devices or understand what numbers mean.

Action: show device, capture context, normalized path, evidence type, and a human label for relevance/quality; hide raw scores by default.

### P1 — Recorder-first and real sync behavior are unproven

Unit tests cover matching logic and Resolve adapter calls, not real recorder files, waveform confidence, ambiguous recordings, drift, or recovery.

Impact: the multi-device workflow can still require manual repair at the most confusing stage.

Action: use real matching/non-matching DJI Mic samples and integrate a proven sync engine before claiming automatic sync.

### P1 — Copy/relaunch fault matrix is missing

Verified copy and cleanup happy/block tests exist, but interruption at every stage and installed relaunch recovery are not proven.

Impact: disconnects or app termination can leave unclear work and invite unsafe retries.

Action: fault injection plus visible resume/retry state.

### P1 — Success and cleanup screens need real verification

The current implementation contains richer per-shoot summaries and progress panels, but they have not been exercised through an installed-app disposable run.

Impact: the user cannot know whether the app is working, stuck, safe to eject, or safe to clean.

Action: installed-app copy/cleanup runs with screenshots and manifest readback.

### P2 — Current top-level information architecture is workflow-numbered but not task-state-led

`Project`, `Import Media`, `Footage Search`, `Project Chat`, and `Activity` are stable, but the user still has to infer the next step from separate pages.

Impact: normal work becomes a guided tour by Codex.

Action: add a persistent project next-action/readiness summary while keeping the editing/search surface distinct from ingest.

## Systemic patterns

- Working backend capability often precedes a clear user-facing decision and recovery model.
- Readiness has improved, but different layers are still easier to conflate than they should be.
- Tests are strong on pure logic and happy-path adapters, weak on cross-stage installed-app journeys and physical source permutations.
- The app has accumulated explanations to compensate for unclear hierarchy, increasing scroll and visual density.
- Fixed profiles remain too close to being the product despite the original `analyze once, understand deeply, query repeatedly` promise.

## Positive findings to preserve

- Per-shoot include and destination choices now exist.
- Partial import is the default, with an explicit `Import all` shortcut.
- Camera WAV sidecars are modeled as hidden children and follow MP4 regrouping.
- Destination SSD and ordinary hard-drive exclusion have automated coverage.
- Verified offload uses aggregate capacity checks, hashes, journals, and preserves sources.
- Cleanup is manifest-scoped, re-hashes destinations, and fails closed.
- Search and Resolve SELECTS reference originals rather than rendered derivatives.
- Resolve confirmation dialogs, frame-rate guards, unsaved-project guards, and timeline reuse tests exist.
- Activity no longer presents idle as a completed green progress bar.
- The Andaan project now demonstrates that narration and visual preparation can coexist, even though the path was not autonomous.

## Audit conclusion

The foundation is real, but the promised product is not yet proven. The correct response is neither to start over nor to celebrate passing suites. Preserve the working subsystems, enforce `PRODUCT_LAW.md`, close the execution gates in dependency order, and require installed-app and real-media evidence before promoting scenario status.
